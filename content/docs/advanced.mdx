# Advanced state and recovery

> **Advanced callout:** this page is for operators diagnosing startup, reconnect, or state convergence. Do not edit a live state file or claim runtime behavior that is not present in the dated evidence records.

## Durable state file

Velocity's `state-file` is a strict JSON object with exactly these fields:

```json
{
  "version": 3,
  "vanished": {
    "01234567-89ab-cdef-0123-456789abcdef": true
  }
}
```

`version` is a non-negative integer. `vanished` maps canonical UUID strings to booleans. Unknown fields, malformed JSON, trailing content, negative versions, non-canonical UUIDs, and non-boolean values are rejected. The writer uses a temporary file and atomic replacement.

A missing file starts as an empty valid state. A corrupt or unreadable file is moved beside the configured `state-file` path using the original filename plus `.bak` (for the default `vanish-state.json`, this is `vanish-state.json.bak`; an existing backup receives a UUID suffix). The proxy attempts a fallback copy if the move fails, but preservation can still fail; verify that the backup exists, and be prepared for manual recovery of the original if it does not. Regardless, the proxy uses an empty invalid state, disables mutations and Redis publication, and does not register the active proxy handlers. This fail-closed path prevents an uncertain state from being exposed. Investigate any preserved file, repair or remove the original only while the proxy is stopped, and restart the proxy.

## Redis protocol

All messages use schema version `1` and strict JSON envelopes.

| Object | Purpose |
| --- | --- |
| `vanish:state:snapshot` | Durable full `vanish_state` snapshot |
| `vanish:state:requests` | Paper change and snapshot requests to Velocity |
| `vanish:state:events` | Versioned `state_delta` events from Velocity |
| `vanish:state:responses` | `change_ack` and `snapshot_response` messages |

A snapshot envelope has `schema`, `type: "vanish_state"`, `version`, and a sorted `vanished` UUID array. A delta has `version`, `playerId`, and desired `vanished`. Requests and responses carry UUID request IDs; snapshot requests/responses also carry `backendId`.

## Snapshot and delta reconciliation

The proxy serializes desired-state changes, persists a new version, updates `vanish:state:snapshot`, publishes a delta, and publishes an acknowledgement. Paper applies a delta only when it is the next version. Older deltas are ignored. A missing or out-of-order version is queued and triggers a full snapshot request. After the snapshot arrives, queued contiguous deltas are drained; an unresolved gap triggers another reconciliation.

At startup, the proxy loads and publishes its durable snapshot, then subscribes to requests. A Paper backend subscribes to events and responses, waits for both subscriptions, and reconciles from the durable key. Paper Redis subscribers retry with bounded exponential backoff (`retry-initial-ms` through `retry-max-ms`). Velocity retries its subscriber at the configured `retry-initial-millis` delay and retries durable-snapshot repair with the same bounded backoff after a failed reconnect write. Pre-login and join paths require a valid state before applying visibility; a valid cached state can be used while a fresh read is retried.

> **Practical warning:** do not run multiple independent Redis databases or use duplicate backend IDs for one proxy. Every backend must reach the same Redis authority and identify itself distinctly for snapshot requests.
